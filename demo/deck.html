Slide 02 / 08 · Why matching fails
The problem

Gradient direction reverses with the sun.

When the sun's azimuth shifts, shadows invert. The bright side of a crater rim becomes the dark side. Standard descriptors encode signed gradient direction (0°–360°) — so the same edge becomes an opposite descriptor. Match confidence drops from ~1,500 inliers to 4.

Gradient-flip diagram — the entire problem in one figure

Why SIFT fails on the Moon

SIFT builds orientation histograms over 0°–360°. A 180° sun shift rotates the gradient at every crater-rim pixel by exactly 180°. The descriptor bin becomes its own mirror image — the same terrain produces a descriptor with maximum possible distance from itself.

The math

∇(1−I) = −∇I

Gradient magnitude is invariant. Gradient direction rotates by exactly π. SIFT measures direction. Our fix: measure orientation (direction mod π) instead.

Slide 03 / 08 · The fix
Our solution

One line of arithmetic eliminates the problem.

Take gradient orientation modulo π. Direction collapses to orientation — which way the edge runs, ignoring which side is bright. Both illuminations map to the same value. This is not a new idea (RIFT, HAPCG, phase congruency use the same family). Our contribution is the benchmark and the pipeline integration.

Move 1 · Scale

GSD from metadata. Resample both products to a common grid with geo.align_pair() before any descriptor is computed. A 320× OHRC–IIRS gap becomes 1×.

Move 2 · Illumination

Mod-π in prep.mod_pi(). Local contrast normalisation strips low-frequency shading. Together they make matching independent of which orbit pass produced the image.

Move 3 · Distribution

8×8 keypoint grid cap. Coverage CV ≤ 0.20. The problem statement explicitly requires "uniform distribution" — we measure it and enforce it, which no baseline does.

Slide 05 / 08 · The finding
A result, not a feature

It is the sun's direction that breaks matching, not its height.

Two separate sweeps — one varying azimuth, one varying elevation at fixed azimuth — produce dramatically different degradation curves. This separates a physical finding from a tuning parameter.

Azimuth sweep (direction)

Sun rotates in the horizontal plane — shadows flip. SIFT crashes immediately. Mod-π holds, then recovers at 180°. This is the failure mode.

Δ AzimuthSIFTMod-πLightGlue
0° 157811671790
30° 38 14 951
60° 4 0 666
180° 4 9071071

Elevation sweep (height)

Sun moves toward zenith — shadows shorten but do not flip. Gradient direction does not reverse. SIFT stays stable. This validates the mechanism. This is not the failure mode.

Elevation 10° → 50°:  SIFT stable
No gradient sign reversal occurs
Separating these two sweeps is what makes azimuth-collapse a finding rather than a curiosity.
Conclusion for ISRO operations
Cross-orbit matching failures at the south pole are driven by orbital azimuth separation, not by the sun's elevation (incidence angle). Re-planning acquisitions to minimise azimuth difference will have far greater impact than minimising incidence angle difference.

Slide 07 / 08 · Pipeline handoff
ISRO integration

One command changes. Everything downstream is untouched.

The output is a native ISIS Control Network (PVL format, .net extension). ISRO photogrammetrists can load it directly into their existing jigsaw bundle-adjustment workflow — no Python, no custom tooling required on their side.

Before LunarMatch

$ findfeatures # fails at 30° sun shift
$ autoseed # no valid tie-points
$ jigsaw # manual intervention

After LunarMatch

$ python -m lunarmatch register \
  --a CH2_OHRC.img --b LRO_NAC.img
# → control_network.net
$ jigsaw fromlist=... cnet=control_network.net
# unchanged command ✓

Control network format

Written to USGS ISIS PVL spec version 5. PointType = Free, MeasureType = RegisteredSubPixel, exact Sample/Line pixel coordinates. Round-tripped through the pvl parser — structure validates. Note: "Written to spec and round-tripped" is true and strong. "Validated in ISIS jigsaw" would require running jigsaw, which we have not done.

Slide 08 / 08 · Where it still breaks
Honest limitations

Four things we would not want a judge to discover.

Naming your own limits in a technical room reads as competence. Hiding them reads as naivety.

🔬

DEM resolution vs OHRC resolution

The premise plot and win plot were generated on NASA SLDEM2015 at 240 m/px. Chandrayaan-2 OHRC sees terrain at 0.25 m/px — about 1,000× finer. Shadow inversion is scale-invariant physics, so the finding almost certainly transfers, but we have not shown it at OHRC resolution. The real end-to-end run is the defence.

🔲

Tiling on repetitive terrain

An OHRC strip is ~54,860 × 12,000 px. Tiling is required. On craters that look alike (repetitive terrain), matching across tiles can produce confident false positives ~1,000 px away from the true position. The fix (coarse phase-correlation pre-alignment, then windowed tile search) is understood but not yet implemented in the production pipeline.

📡

IIRS not implemented

The problem statement includes ISRO IIRS hyperspectral data. We have CH-2 OHRC and LRO NAC readers. IIRS has a different data format and spectral structure. Our pipeline does not handle it yet. This is a real scope gap.

⚙️

ISIS jigsaw compatibility — not tested end-to-end

The control network is written to the documented PVL spec and round-trips through the pvl parser. We have not run jigsaw on it. "Written to spec and round-tripped" is accurate and defensible. "ISIS-validated" would require actually running jigsaw, which we have not done. Do not say the latter.
